# Dance Studio

マネキンが踊る**無音動画**を作るアプリ。そのまま完成品にするものではなく、
Domo AI のような映像変換サービスに通してキャラクターに置き換えるための
**素材動画**を作るのが目的。音は変換が終わったあとに動画編集側で合わせる。

公開先: https://dopagakiorchestra.github.io/dance_studio/

## 使い方

1. BPM・拍子・小節数・くり返しを決める
2. 振り付けが自動で組み上がるので、気に入らなければ「引き直す」
3. ブロック単位で振りを差し替える（手で選んだところは引き直しても残る）
4. 「動画を書き出す」

手元の曲を読み込むと、プレビューをその音に合わせて見られる。
この音は書き出す動画には**入らない**。

## 開発

```sh
npm install
npm run dev      # 開発サーバ
npm test         # テスト
npm run build    # 型チェック + ビルド
```

React + Vite + TypeScript。実行時の依存は react / react-dom と、
動画の取り込みに使う @mediapipe/tasks-vision だけ。MediaPipe は動的 import で
別チャンクに分けてあるので、動画を取り込まない限り読み込まれない。

`npm run build` / `npm run dev` の前に `scripts/fetch-pose-assets.mjs` が走って、
姿勢推定の WASM とモデルを `public/pose/` に用意する（リポジトリには入れない）。

## 構成

```
src/
├─ dance/            振り付けとマネキン描画（音楽に依存しない中核）
│  ├─ skeleton.ts     骨格、順運動学、左右反転、ポーズ補間
│  ├─ moves.ts        1小節（4カウント）単位の振りパーツ辞書
│  ├─ choreo.ts       曲構造からパーツを並べる生成ロジック
│  ├─ sampler.ts      時刻→ポーズ（補間・繋ぎ・ビートの上下動）
│  ├─ ground.ts       接地の解決（脚の逆運動学）
│  ├─ depth.ts        深度マップ描画（既定の見た目）
│  ├─ landmarks.ts    姿勢推定の点群 → この骨格のポーズ（リターゲット）
│  ├─ capture.ts      動画 → 動き（MediaPipe Pose。ブラウザ専用）
│  ├─ render.ts       canvas描画（投影、画角の自動決定、配色）
│  └─ video.ts        canvas.captureStream + MediaRecorder
├─ components/DanceStudio.tsx  プレビュー・設定・ブロック一覧・書き出し
├─ audio.ts          音源ファイル再生（プレビュー同期用。動画には入れない）
├─ project.ts        設定モデル、localStorage、共有リンク
├─ compat.ts / save.ts / mp4.ts   保存まわり（iOSの癖対応）
└─ App.tsx           画面全体

tests/dance.test.ts, tests/project.test.ts
```

## 設計上の決定

変える場合は、まず理由を確認すること。

- **既定の見た目は深度マップ。** マネキンの絵柄を変換サービスに渡すと、
  変換側は「その絵をどう解釈するか」から始めることになる。深度マップなら
  形そのものを渡せるので解釈の余地が減り、色も陰影も持たないぶん変換後に
  元の見た目が残らない。手前が白・奥が黒（MiDaS / ControlNet の depth に
  合わせた向き）。マネキンの絵も「描き方」で残してある
- **深度を明るさで表しているので、合成を `lighten` にすると z バッファになる。**
  canvas 2D に深度テストは無いが、チャンネルごとの最大値＝一番手前が勝つ。
  描く順番が結果に影響しなくなるので、マネキン側でやっている画家のアルゴリズム
  （奥から順に描く）が要らない。手足が交差しても正しく隠れる
- **明るさの正規化は振り付け全体で1回。1コマごとにやってはいけない。**
  手が前に出た瞬間だけ基準が変わって、動画全体が脈打つ。画角とまったく同じ
  理由で、範囲は先に走査して固定する（`Stage.depthNear` / `depthFar`）
- **深度マップには鼻を付ける。** 色が無いので「顔の面を塗って正面を示す」手が
  使えない。頭の手前に球を置くと、頭が後ろを向いたとき深度テストが勝手に
  隠してくれるので、描く側で向きを判定しなくてよい
- **体は球を並べて作る。** 骨は「両端の球を繋いだテーパー付きカプセル」なので、
  軸に沿って半径を補間しながら球を並べれば和集合が正確にカプセルになる。
  球ひとつの深度は解析的に出る（中心から t の位置で d - r√(1-t²)）
- **振りの系統は「かっこいい・妖艶・かわいい・指揮」。** 以前あった「基本」の
  11個（肩ゆらし・手拍子・ランニングマンなど）は地味で、混ざると全体が
  素人くさくなるので消した。キメ2つは「かっこいい」へ移してある
- **生成に使う系統は選べる（`DanceSettings.styles`）。** 指揮の振りをダンスと
  同じ袋に入れておくと、普通の振り付けの途中で突然タクトを振り始める。
  既定はダンス3種で、指揮は明示的に選んだときだけ出る
- **指揮は体を斜めに向ける（`PODIUM_TURN` = 22度）。** 指揮はほぼ全部が
  「前へ差し出す」動きなので、正面固定のカメラだと前腕が短縮して消え、
  手が顔の横に上がっているようにしか見えない（実際そうなった）。斜めにすると
  前後が画面上の左右に化けて読めるようになる
- **指揮の腕の角度は「手をこの位置に置きたい」から逆算した。** 手で当てると
  必ず腕が伸び切るか肘が張るので、目標位置に対して総当たりで解いて丸めてある。
  解は複数あるので、角度の小さいほう＝自然な形を選ぶよう罰則を入れている
- **指揮の振りは2系統ある。** 上半身だけの20個（拍子・強弱・合図など）と、
  膝と高低差を使う20個（沈んで出す・立ち上がって膨らませる・踏み込むなど）。
  上体だけ動かしていると、どれだけ腕を振っても「腕の運動」にしか見えない
- **沈むときは必ず膝を曲げること（`podium` の `drop`）。** 腰を下げるだけだと
  両足が床にめり込み、**接地の解決が体ごと持ち上げ直してしゃがみが消える**。
  太もも -α・膝 +2α で足首を真下に留める（sampler の上下動と同じ式）。
  実測で、書いた沈みの 100〜148% が最終的な腰の上下として残っている
  （超えるのはダイナミクスの行き過ぎとビートの上下動が乗るため）
- **つま先立ちは足首を伸ばした分だけしか上がれない（`podium` の `lift`）。**
  腰を上げるだけだと足が床から離れ、接地の帯（`PLANT_BAND`）を超えて宙に浮く
- **横への踏み替えは腰の平行移動ではなく踏み込みで作る（`lunge`）。** 接地の
  解決は縦しか見ていないので、腰を横へ動かすと足がそのまま滑る
- **指揮の下半身は「踊らない」。** 膝は使うが、拍に合わせて弾ませるのは
  `kneeBeat` だけ。全部の振りで足を弾ませると指揮者に見えなくなる
- **手で選んだ小節が何小節あるかを画面に出す。** 引き直しは手動の小節を
  飛ばす仕様なので、全部が手動だと押しても何も起きない。しかも**左右反転の
  チェックを付け替えただけでもその小節は手動になる**ので、本人に手で選んだ
  つもりが無いまま全部が固定されていることがある（実際にそうなった）。
  数と理由を出して、まとめて自動へ戻せるようにしてある
- **手で選んだ小節は系統の絞り込みを無視する。** 「指揮だけ」にしても、
  前に手で選んだダンスの振りはそのまま残る。画面では「系統の外の振り」として
  数を出す（黙って消すと、選んだはずのものが消えたように見える）
- **振りを差し替える単位は1小節（4カウント）。** 以前は2小節単位だったが、
  同じ振りが2小節続くうえ「次はその左右反転」と読めてしまって単調だった。
  手動指定はスロット番号で覚える（並び順で覚えるとシードを引き直したときに
  別の小節へずれる）。ボックスステップと半回転だけは2スロット使う
- **ノリは縦（沈み込み）と横（重心の左右移動）を混ぜられる。** 縦だけだと
  スクワットに見えることがある。横は拍ごとに乗る側が入れ替わるので周期は2拍
- **足は床に置く。腰の角度で近似しない（`ground.ts`）。** それまでは床という
  概念が無く、脚は骨盤からぶら下がっているだけだった。沈み込みも体重移動も
  「腰を動かした分を太ももの角度で打ち消す」近似で、実測では足が床を腰高の
  10% 突き抜けていた。2ボーンIKで解くと、ノリの有無による足の高さのずれが
  縦 0.069 → 0.003、横 0.033 → 0.001 になる。**これは見た目の話ではなく、
  ノリが本物になるということ**（それまでは沈んだ分だけ足も沈んでいたので、
  沈み込みが床に対しては起きていなかった）
- **両足とも沈んでいるなら腰ごと持ち上げ、片足だけならその脚を縮める。**
  片足の沈みを腰の上下で直すと跳ねたように見えるし、両足の沈みを脚の曲げで
  直すと、立っているだけなのに膝が曲がる
- **接地とみなす帯は狭くする（`PLANT_BAND`）。** 床のすぐ上に浮いた足は床へ
  下ろすが、広げるとステップで上げた足まで引かれて振りが潰れる。上げた足は
  腰高の 33% まで行くので、そこに触らない値にしてある
- **接地した足の裏は床と平行にする。** 骨格の足は描かれる太さまで含めると
  7度ほど前下がりで、そのまま置くとつま先立ちに見える。ただし振り付けが
  足首を寝かせているところ（つま先立ち・かかと上げ）は意図なので触らない
- **膝の曲がる向きは、いま曲がっている向きをそのまま使う。** IK の定石どおり
  「前向き」で決め打ちにすると、脚を開く振りで膝の向きが変わる。いまの膝の
  位置から曲がる面を取れば、狙いが今の位置と同じなら答えも今のポーズになる
- **接地の解決は `sampleSkeleton` で掛ける。** `samplePose` は振り付けそのものを
  返す層にしておきたいので、床の都合を混ぜない
- **ポーズは時刻だけの関数のままにする。** 「前のフレームで足を置いた場所」を
  覚えれば横滑りも直せるが、画角の走査も書き出しもランダムアクセスできなく
  なり、同じ時刻を2回サンプルして違う結果が出るようになる。**そのため直せて
  いるのは縦方向だけで、接地した足の横滑りは残っている**
- **足元の影は足ごとに1つずつ置く。** 腰の下にひとつだけ置くと、どちらの足に
  体重があるのかが出ない。床を描いていない以上、接地の効果はここでしか見えない
- **体は「骨盤 → くびれ → 胸郭」で太さを変える。** 同じ太さのカプセルを積むと
  筒に見えて、人の体だと読めない。くびれと肩幅の差がシルエットの決め手。
  膝下でいったん太くしてから足首へ絞るとふくらはぎになる。足先は尖らせない
  （尖るとつま先立ちに見える）
- **頭は縦長の卵形。** 真円だと何をしてもボールに見えるし、首を傾けても
  分からない。傾きは首から頭頂への向きを画面上で測って合わせる
- **手は手のひらと指の2節に分ける。** 長さと幅が同じだとグーに見え、1本の
  細長い棒にすると今度は手刀に見える。どちらも「指の付け根で折れる」という
  手の特徴が出ていないのが原因。折れは必ず指の付け根に置くこと（手首で折ると
  「手を反らせている」になる）。先端は尖らせない（尖ると刃物に見える）。
  指の丸まりは sampler が既定で入れる（`FINGER_CURL`）ので、振り付け側は
  手を書かなくてよい
- **カメラは正面固定。前後（X軸）の動きはほとんど見えない。** 背骨を前後に
  波打たせても正面からは何も起きていないように見える。前後を見せたい振りは
  hips の Y 回転で体を斜めに向けること（`bodyWave` がそうしている）。
  ただし**深度マップにすると前後が明るさに出る**ので、この制約は少し緩む
- **回転する振りは、始点と同じ向きで終える。** オイラー角の補間は最短経路を
  選ばないので、360度まで回して終わると次のブロックへ繋ぐときに逆回転で
  巻き戻る。実際に「半回転」がそうなっていた（回して戻る形に直した）。
  腰（hips）を回すと脚ごと向きが変わるので、上半身だけ向けたいときは chest を使う
- **キメは動きの大きさで絞らない。** energy で選ぶと一番大きいキメ1つだけが
  毎回出てきて、締めが完全に読めてしまう
- **入力は BPM・拍子・小節数・くり返しの4つだけ。** 振り付け生成にコード進行や
  メロディは使っていないので、音楽理論のコードは持ち込んでいない
- **ポーズは関節の位置ではなく回転で保持。** 補間しても骨の長さが変わらず、
  左右反転が符号反転（Y,Z を反転、X はそのまま）で済むため
- **肘が曲がるのは X（前後）と Z（横）だけ。** 前腕は -Y 方向に伸びているので、
  Y 回転は軸まわりのひねりにしかならず見た目が変わらない。ここを取り違えて
  肘の指定19箇所が無効になっていたことがある。`elbow()` / `elbows()` を使い、
  生の配列で前腕を書かないこと（テストで検出される）
- **肘は伸ばし切らない。** 既定で少し曲げ（`ELBOW_REST`）、腕を上げた分だけ
  sampler が追加で緩める（`ELBOW_SOFT_MAX`）。伸び切った腕は棒に見える。
  振り付け側が大きく曲げているところには手を出さない
- **キレは「速く動く」ではなく「速く動いて止まる」で作る。** キーフレーム間を
  丸ごと使って動き続けると、どれだけ鋭い曲線を使っても体操にしか見えない。
  `snap`（ダイナミクス）が到達を早めて残りを静止に回し、行き過ぎてから戻り、
  振り幅・上下動・繋ぎの詰めまでまとめて動かす
- **振り幅の拡大は上半身だけ。** 脚と腰には掛けない。`weight()` が足の位置を
  角度で打ち消していて、`turnHalf` は hips の回転量そのものでターンを作って
  いるので、一律に倍率をかけると足が浮いたり回転角が変わったりする
- **画角の走査は 0.05 カウント刻み。** 粗いと、速い動きの行き過ぎた一瞬を
  跨いで見落とし、本番でそのコマだけ手足が画面外へ出る（実際に踏んだ）
- **ビートに乗った上下動が最重要。** これが無いと「ポーズの連続」に見える。
  腰を沈めた分だけ膝を曲げて足首位置を保つ（太もも α・膝 2α）
- **上下動は左右非対称にする。** ゆっくり伸び上がって素早く落ちる。対称な cos
  で上下させると浮いて見え、落ちを詰めると重さが出る（`DROP_SHARE`）
- **追従（二次運動）は加速度から作る。** ばねの過渡応答を積分すると、ポーズが
  「それまでの履歴」に依存して時刻だけの関数でなくなる。代わりに減衰の弱い
  ばねの低周波展開 `y ≒ x - 2ζ/ωn・ẋ + (4ζ²-1)/ωn²・ẍ` を使い、遅れの項は
  `chain` に任せて加速度の項だけを引く。振り終わりに越えて戻り、振り始めに
  わずかに引く。`snap` の行き過ぎが全関節に同じ形で掛かる決め打ちなのに対し、
  こちらは実際にどれだけ急に止まったかで量が決まる。
  **代償は手先の最高速度**（0 で 10.6、既定 0.35 で 12.4、1 で 16.4 身長/秒）
- **体の連鎖（腰→胸→肩→手先）で到達を遅らせる。** 全関節が同時に到達すると、
  人形が一斉に折れ曲がったように見える。これが硬さの正体。
  遅れを入れても**手先の最高速度は上がらない**（通る距離も時間も変わらないため）
  ので、映像変換のリスクを増やさずにキレを足せる数少ない手段
- **キメのブロックだけ繋ぎを狭くする。** 通常の繋ぎ幅だと締めの前後が常に
  クロスフェードに食われ、キメが丸まる。狭くするほど手先が速くなるので、
  「動きが飛ばない」テストの実測値を見ながら 0.14 カウントに置いてある
- **ブロックの繋ぎは境界の前後に均等なクロスフェード。** 後ろだけで繋ぐと
  手先の速度が3倍近くになり、映像変換で破綻する
- **画角は振り付け全体を先に走査して決める。** 手足が画面外に切れないため。
  動画1本の中では固定
- **動画は無音。** 変換サービスを通すと音は落ちるか尺がずれるので、音は別管理
- **形式は H.264 の MP4 を最優先、無理なら WebM。** コーデック指定なしの
  `video/mp4` を上位に置くと VP9 入り MP4 が返ってきて、拡張子が .mp4 なのに
  多くのツールで開けないファイルになる

## 体型

映像変換は入力のプロポーションを参照するので、変換後のキャラクターの体つきは
素材側で決まる。頭身・脚の長さ・腕の長さ・太さ・肩幅を変えられる。

**背丈そのものは画面上の見え方に出ない。** 画角は振り付け全体に自動で合わせる
ので、一様に大きくしても同じ大きさに収まる。効くのは比率のほう。

振り付けは「脚の長さが標準」のつもりで書かれている。`solvePose` が腰の位置を
まとめて脚の倍率で伸ばすので、しゃがみの深さも横への体重移動も同じ比率で
付いてくる（`weight()` が足の位置を打ち消すのに使う角度も、比が変わらないので崩れない）。

頭身の表示は、骨格上の頭の長さではなく**実際に描かれる球の直径**で割っている。
見ている人が数えるのはそちらなので、骨格上の値で出すと実物より小さい数字になる。

## 既知の制約

- 録画は実時間かかる（MediaRecorder の仕様）。裏タブだと rAF が止まるので、
  書き出し中はこのタブを開いたままにする必要がある
- 出力ファイルは尺が「不明」として記録される。ブラウザ録画では避けられない。
  ffmpeg を通すサービスなら問題にならない
- **動きの質は手作りパーツの組み合わせの限界がある。** プロの振付師のタメや
  間は出ない。映像変換は絵柄を変えるが動きの硬さは残る
- **ダンスの振りはキーフレームが表拍にしか無い。** すべて整数カウント上にあり、
  「1 と 2 と」の“と”が1つも無い。キレの多くは裏拍の当て方で決まるので、
  ここは伸びしろとして残っている（moves.ts に書き足す作業）。
  指揮の「3拍子」「刻みを細かく」「スタッカート」だけは裏拍に置いてある
- **接地した足が横に滑る。** ポーズを時刻だけの関数に保っているので、足を
  置いた場所を覚えていない。縦は解けているが横は手つかず。次に直すならここ
  （「直前の拍の頭での足の位置」を基準にすれば、履歴を持たずに解ける）
- **足が床に届かない一瞬がある。** 脚を伸ばし切っても届かないとき、腰を
  下げれば届くが、それをやると「背伸びする振り」まで潰れるので触っていない。
  残るずれは腰高の 1% ほど
- **深度マップを変換サービスに通していない。** 深度は ControlNet 系の標準的な
  入力なので通るはずだが、Domo AI がそれを depth として扱うのか、ただの
  グレースケール映像として扱うのかは未確認。だめならマネキンに戻せる
- **深度マップの階調は振り付け全体の前後幅で割られる。** 手を前に突き出す振りが
  1つでも入ると範囲が広がり、他のコマの体の階調が浅くなる。脈打たせないための
  代償で、いまは全体の実測幅をそのまま使っている
- **手先の速度は既定でかなり速い。** ダイナミクス 0.75・追従 0.35 で
  手先が最高 12.4 身長/秒、全身では 20.5 身長/秒。映像変換がフレーム間で
  追随できるかは**未検証**なので、破綻したら「ダイナミクス」と「追従」を
  下げて調整する
- **取り込んだ動きは保存されない。** 300コマぶんの関節角度で数百KB あり、
  共有リンクに載せると開けない長さになる。ページを開き直すと消える
- **どの段階にも待ち時間の上限を置くこと。** 置いていなかったせいで、読めない
  動画を渡すと無言で止まったままになっていた。読み込み 20秒・コマ送り 10秒・
  モデル 120秒で打ち切って、必ず理由を返す。何も起きないのが一番たちが悪い
- **iPhone の .mov（HEVC）は Chrome や Firefox では開けない。** `canPlayType` で
  選んだ時点で判定して、MP4（H.264）への変換か Safari を案内する
- **取り込みは実写で試していない。** 手元に人の写った動画が無く、検証は
  自分のマネキンを録画したものだけ。実写での精度は未確認
- **重心を見ていない。** 支持している足の上に体重が乗っているかを誰も
  確かめていない。ただし実測では支持足がある 640 コマのうち重心が支持基底から
  外れているのは 6.7% で、しかも `backStep` `slideStep` `turnHalf` の3つに
  集中している。全身の重心拘束を入れるより、その振りを直すほうが早い

## 公開

`main` への push で GitHub Actions がテスト・ビルドして Pages に公開する
（`.github/workflows/deploy.yml`）。Pages が未設定でもワークフローが自分で
有効化する。ただし**無料プランでは Public リポジトリでないと Pages が使えない**。

## 動画から動きを取り込む

踊っている動画を読み込むと、MediaPipe Pose で 33 点を取り、`landmarks.ts` が
この骨格の関節回転に移す。

- **点をそのまま関節位置にしない。** 位置で当てると骨の長さが毎コマ変わる。
  「骨の向き」だけを取り出して回転に直すので、被写体の体格が違っても手足が
  伸び縮みしない
- **ねじれは曲がっている面から決める。** 骨の向きだけでは軸まわりが決まらない。
  上腕のねじれは肘がどちら側へ出ているかで決める（`ground.ts` の膝と同じ話）
- **骨盤は上体の傾きに 0.3 しか付いていかない（`PELVIS_FOLLOW`）。**
  「腰の中点→肩の中点」をそのまま骨盤の上向きにすると、上体を前に倒しただけで
  骨盤ごと回り、脚が後ろへ振れる。実際そうなった
- **足首→つま先は前向きに伸びている。** 他の骨と同じに -Y 向きだと思って
  組むと 77 度ずれ、つま先が身長の 15% ずれる（`FOOT_REST`）
- **腰の横移動は取らない。** world landmarks は腰が原点なので平行移動が
  入っておらず、画像側の点から取るとカメラの動きと混ざる。上下だけは足の
  位置から復元する（しゃがみは拾える）
- **取り込んだ動きには味付けを掛けない。** ノリ・ダイナミクス・追従・体の連鎖は
  手作りのパーツを生き物に見せるための処理で、本物の動きに足すと二重になる。
  接地だけは掛ける
- **資材（WASM 11MB・モデル 5.5MB）はビルド時に用意してリポジトリには入れない**
  （`scripts/fetch-pose-assets.mjs`、`public/pose/` は .gitignore）。CDN から
  読むと変換したい場面でネットワークに振り回される。読み込みは `import()` で
  分けてあるので、この機能を使わない人は落とさずに済む
- **MediaRecorder で録った動画は尺が「不明」になる**（このアプリの書き出しも
  そう）。そのまま信じると 4秒の動画を 30秒として読み、残りは最後のコマが
  止まったまま並ぶ。ありえない時刻へシークさせて尺を確定させている

### どこまで正しいか（実測）

リターゲットだけを検算した結果（こちらの骨格から点群を作って戻す。答えが
分かっているので、座標系の取り違えがあれば即座に出る）:

```
頭頂 7.5% ／ 手足 4% 前後 ／ 脚 2.2%   （身長に対する関節位置のずれ）
```

自分のマネキンを録画して通した端から端までの実測は **20%**。時刻のずれと
均しの影響を差し引いても変わらないので、差は**推定器そのものの精度**。
ただし題材が「のっぺりした灰色のマネキン」で、人の写真で学習した推定器には
一番不利な入力なので、**人が写った実写ならもっと良くなるはず**（未検証）。
